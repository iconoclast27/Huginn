### F26 fix: infra failures do not become corrections

**Discovery:** `Agents/Huginn/MEMORY/corrections.md` contained `type: schema-error / key: LLM client returned null` — an Ollama infra failure (timeout/abort/HTTP) had been recorded as a model mistake and injected into every future tag-assignment prompt via `corrections.getContext()` (keyed by recipe name, not target note).

**Root cause:** in `harness.run()`, a null LLM result pushed `'LLM client returned null'` into `schemaErrors` → `schemaValid === false` → the unconditional corrections block appended a `schema-error` entry.

**Fix:** `clientFailed` flag set when `raw === null`; the corrections block is now guarded by `!clientFailed`. Genuine schema errors and apply failures still write corrections (F13 unchanged and green). Deliberate scope cut: `clientFailed` is not exposed on `RecipeRunResult` yet — when a consumer needs it, the `types.ts` change is its own fixture-first task.

**Process:** fixture-first, red earned and certified before the fix (`src/fixtures/f26.ts`, asserts on the real run result and an append-call counter — not text-grep proxies), full bench green: typecheck, F01–F26, build. F26 wired into the `npm run fixtures` chain; README/TESTING1 updated to F01–F26.

**Open sub-item:** the original 80-second null failure's *cause* is still undiagnosed — we fixed the consequence, not the timeout/HTTP failure itself. When it recurs, capture the `[Huginn] Ollama chat timed out` / `HTTP <status>` console line.
