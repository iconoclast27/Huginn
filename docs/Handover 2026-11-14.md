## What got built (uncommitted, at Dan's Hold)

### 1. `tag-assignment` up to two tags + the ground-truth strip seam — `f29`

Spec rulings Dan made in this session, each honoured in code:
- "Up to two tags": the recipe's prose proposes **up to two**; no ceiling is enforced in code. A 3-tag proposal is accepted by validation, all three are judged by ground-truth, survivors are applied (f29 S4).
- **Strip, not reject**: a proposed tag already present in the note's frontmatter is **dropped**, not refused; the remaining proposals survive the verdict, show in the approval modal, and are applied (f29 S2).
- `reason` stays **one sentence covering the whole proposal** (no per-tag reason).
- Dropped values write **no correction** — a duplicate tag is not a rule failure, and f13 S2 ("no rule failure, no correction") is the governing invariant.
- `tags` becomes an **array of strings** (`minItems:1, maxItems:10`), `valuePath: "tags"` resolves the top-level array, validation path `/tags` (so `tags: []` fails validation — `minItems` applies at `/tags`, not per element).
- No hard min/max enforcement: Dan rejected `minItems`/`maxItems` as a rule-enforcement mechanism. **Why, verified:** `parser.ts`'s `schemaKeyword` (lines 299-307) accepts only `type`/`items`/`properties`/`required`/`enum`, so `minItems`/`maxItems` never reach the validator; a 3-tag proposal would become a `schema-error` correction, appended to `corrections.md` and injected into every future `tag-assignment` prompt — the memory-pollution vector of the creativity-death symptom. The floor needs no machinery: `tags: []` → validation passes at `/tags`, `valuePath` resolves `[]`, `applyRoutine` returns `applied:false` `No tags provided; nothing to apply.`

The seam (the machinery the rulings required):
- `groundTruthValid` gates approval and apply (`harness.ts:121`), so survivors must be **computed**, not just judged — the harness needed a strip stage between validation and approval.
- All six built-in primitives return `{ errors, drops }` with per-element array semantics (a value present in frontmatter is a `GroundTruthDrop`; drop is fatal only when **every** proposed value is dropped). Scalar messages are byte-compatible with the previous strings, so `f03`/`f24` stayed green untouched.
- `stripGroundTruthDrops()` removes dropped values from the output; diff, gate, and apply all consume the stripped state.
- `RecipeRunResult` gains `groundTruthDropped: string[]` — that is what the UI drops the notice into.
- **Extension-point compatibility, the important design point:** primitives were briefly `errors`-only (rejected: no way to record a drop). Making them return `PrimitiveOutcome` only broke `f17` — `TypeError: outcome.drops is not iterable` at its extension primitive — because `f17` is the documented third-party extension seam (`docs/Huginn Plugin 2 Harness.md §Adding a custom primitive`), and `f17` S1/S3 passing is the contract that keeps it valid. The fix: `PrimitiveResult = ValidationError[] | PrimitiveOutcome` + `normalizePrimitiveResult()`, so both the documented shape and the new shape work. `f17` green, harness and fixture clean.

## The f30 park — and Dan's two questions, answered

**What I built:** `dev/parked-ui-stop-fixture/` contains `f30.ts` (the UI-leg Stop fixture: Stop during dispatch, Stop while the approval modal is open, panel reuse after a Stop, close mid-flight), `f30-probe.ts` (the import probe that proved the seam works), `obsidian-shim.ts` (a fake Obsidian runtime: DOM, `Modal`, `Setting`, `MarkdownRenderer`, `ItemView`, `Workspace`), and `tsconfig.test.json` (maps `'obsidian'` → the shim; run as `npx tsx --tsconfig dev/parked-ui-stop-fixture/tsconfig.test.json dev/parked-ui-stop-fixture/f30.ts`). It is parked at Dan's ruling, never wired into the chain, **never run**, and kept outside `src/**` so `npm run typecheck` stays green.

**Why it exists at all:** `import { ... } from 'obsidian'` throws `ERR_MODULE_NOT_FOUND` under `tsx` — `node_modules/obsidian/` ships only `obsidian.d.ts`/`publish.d.ts`/`canvas.d.ts` (`main: ""`), no runtime module. So a fixture cannot import `chat-view.ts` without a mapped fake. `f06`/`f08` avoid the problem by building gate wrappers that don't import `obsidian`.

**Q — Did you consult the section under `node_modules` that has the Obsidian API references before doing this?**
**No.** I listed `node_modules/obsidian/` (and confirmed only `.d.ts` files, `main: ""`), and grepped `src/**` for which Obsidian APIs the plugin uses, but I did **not read `node_modules/obsidian/obsidian.d.ts`** — which is exactly the reference Dan means, and the only authoritative source for the signatures a shim must reproduce. I derived `Modal`, `Setting`, `MarkdownRenderer`, `ItemView`, `Component`, `WorkspaceLeaf`, `App` signatures from the plugin's own call sites (`chat-view.ts`, `approval-modal.ts`, `main.ts`). That is why the shim came up incomplete: `ShimHandle` lacks `setButtonText`, `setCta`, `setWarning`, `onClick` — all called on `Setting` handles by `approval-modal.ts` (lines 57, 71, 82, 104, 108) — so `f30`'s S2 fails the moment the modal renders. **Any continuation must start by reading `obsidian.d.ts`** (`Modal`, `Setting`, `SettingButton`, `Component`, `MarkdownRenderer.render`, `ItemView`, `WorkspaceLeaf`, `App`) and matching the shim to it, not to call sites.

**Q — Is this not something that could have been tested in the release?**
**Yes — fully.** Scenario F's UI leg is observable in a real Obsidian run, and the manual smoke tests exactly what the shim can only imitate (modal lifecycle, DOM, plugin wiring): with a chat request in flight, press Send → the modal closes, `[Interrupted]` appears in the chat, the note is unchanged, and **no** refusal correction is appended to `corrections.md`; then close the panel mid-flight → no `Chat view` error in the console, the panel reopens, a follow-up request runs. `docs/TESTING1.md` Scenario F already carries these steps. So the release smoke is the **cheaper and more faithful** path for this leg; the shim's unique value is only build-time regression protection.

**And the finding that reframes the leg:** **the UI Stop path has no production bug.** `chat-view.ts` `handleSend` treats Send as Stop while a request is in flight (`abort()` + `ApprovalModal.closeActive()`, lines 229-234); `ObsidianApprovalGate` (approval-gate.ts:38-46) closes the modal on abort and resolves `null`; `ApprovalModal.onClose` does not resolve the gate, so the abort wins the promise race; `harness.ts` skips apply and records no correction when the gate returns `null` (`:142`); `main.ts` wires `ObsidianApprovalGate` for both chat (line 122) and batch (line 249).
